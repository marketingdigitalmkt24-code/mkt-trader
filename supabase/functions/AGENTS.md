- Sequência de 3 sinais (SEQUENCIA_3_SINAIS, claim_after_signal_sequence, prefix sequencia-3-v1-) runs beside Após 5 LOSS in selected-demo-trend: the 3 latest confirmed Demo orders (strategy:direction:result) must match a user set kept identical in _shared/signal-sequence.ts and the SQL claim; the next fresh Demo signal opens following or inverted per set, with copies/Telegram. Takashi invertida and Nota consistente are retired (claim execute revoked, history/labels kept). Why: user-chosen principal rule; historical eligibility alone must never place money-moving orders.
- Minute scan status uses three private rotating Storage objects and one last-completed per-asset snapshot written by the service and read only by an authenticated admin function; absent signals carry null notes, phases include preparation, scan, completed-without-candidate and failure, writes stay off the placement critical path. Why: show actual consulted markets through reconnection without fake scores, signals or public telemetry.
- Demo recovery sizing uses the actual confirmed predecessor amount, keeps tie stakes and resets on cycle completion; payout is metadata, not a recovery sizing input. Why: all fresh Demo reservations must follow the same progression without fabricated losses or payout-dependent stake changes.
- Demo normal-minute selection ranks current calculated scores only among broker-available M1 markets, without historical winning-note priority or WIN-chart gates; preserve learning. Recovery ignores expired unknown/reserved attempts only without broker IDs, leaving their unknown outcomes intact and using the latest confirmed result; unexpired ambiguity, broker-ID pending orders and insufficient balance still block. Why: stale attempts must not strand new signals or fabricate recovery losses.
- Principal placement/copy and Telegram use unconditional shared pause gates before any claim. Daily reports stay paused; Demo/settlement independent; why: every executor must respect the full stop without changing confirmed history.

- Demo prepares before :00 and sends fresh Takashi on that PRACTICE socket. Refresh expired pending IDs after :00 and retry history at :01/:03/:06/:10/:15 concurrently with scanning/placement; stop when none remain, conditional exact-ID writes only, preflight login attempts repeated until 3s before :00, never after; why: early snapshots/history must not miss just-confirmed orders or delay selection. Broker unavailability never fabricates signals/results.
- The run that confirms a Demo order keeps its socket (heartbeat answered) in background until that order's own expiry and runs the same exact-ID history retries; why: the next minute's broker login often times out, which delayed results by minutes.
- All frontend broker balance callers share one in-flight request and minimum interval; polling effects never restart on status transitions. Demo preflight retries HTTP login across rotating hosts (per-host cap, browser UA) until only a socket reserve remains, falling back to direct WebSocket auth last, and retries HTTP after both socket endpoints fail only with handshake budget remaining; use the resolved master credentials and verified PRACTICE USD profile before the original deadline; the master broker session may be reused across minutes only through the service-only `iq_broker_sessions` cache (cleared when the socket refuses it), never logged or returned; never retry placement. Why: an unavailable gateway must not consume the entire analysis minute or cause stale/duplicate trades.
- Demo TEST: isolated, one/minute, no copy; singleton admin-only stake settings snapshot amount per order, unique minute/type-4 USD, exact-ID reconciliation across portfolio/legacy pages. Principal orders use shared copy with own account/stake/limits/expiry; selected Demo claim validates outcome triggers atomically, returned direction/strategy drive IQ/results/Telegram; why: no amount mixing, rewrites, replay or competing orders.
- Demo candidate scoring learns from confirmed Demo outcomes plus real principal IQ results (1.5x weight) and rejected candidates with live-price TEST outcomes (0.5x weight) per strategy/hour/asset and chart shape; strongly negative combined scores are rejected before selection; why: prioritize patterns with proven real profit without guaranteeing gains.
